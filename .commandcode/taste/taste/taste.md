# Taste
- Treats the PRD as the canonical source of truth when documentation conflicts; when docs are out of sync, resolve the conflicts against the PRD rather than the stale design docs. Confidence: 0.6
- Wants coding conventions (naming, file/folder structure, code style) documented in a dedicated markdown doc covering both backend and frontend, grounded in industry best practices and common usage rather than ad-hoc rules. Confidence: 0.5
- Treats the PRD as a living, versioned document: when requirements change, expects the PRD updated first (new version + change-log entry) before the change cascades to the design docs, conventions/planning, and code. Confidence: 0.5
- Prefers a detailed, phased TODO/plan (broken down by build phase and dependency order, grounded in the PRD/design docs) laid out before implementation starts; a plan should include a decisions/rationale section (each choice with its reason) and be approved before coding begins. Confidence: 0.65
- Wants planning/TODO artifacts persisted as versioned markdown docs in the repo (e.g. `docs/PLANNING.md`) with trackable checkboxes, rather than only living in ephemeral tool/task-panel state. Confidence: 0.55
- Prefers operational "how to run the project" setup documentation written as its own dedicated markdown file in the repo (e.g. `docs/RUNNING.md`), kept separate from behavioral/convention docs; expects it to be precise about configuration realities (which env file is actually loaded, e.g. `.env` not `.env.example`) and default credentials. Confidence: 0.5
- Strongly dislikes guessing: when requirements are ambiguous, expects the agent to investigate existing code/docs for grounding and ask explicit clarifying questions before making changes, rather than assuming. Confidence: 0.7
- Treats the documented conventions doc as the authoritative standard for structure and naming, and expects the code to be refactored to conform to it (e.g. "fix canonical backend structure based on conventions.md"). Confidence: 0.6
- Prefers unused/out-of-scope scaffold code be removed rather than left in place, and authorizes deleting modules that aren't needed for the project being built. Confidence: 0.5
- Wants request/response types shared between backend and frontend via a common package under `packages/`, synced through the monorepo workspace as a single source of truth, rather than duplicated per app. Confidence: 0.5
- Expects the agent to run and pass the full workspace verification suite (top-level lint, build, and tests) before reporting work as complete, rather than just building the touched app. Confidence: 0.55
- Wants to approve new dependencies before they are added rather than having them introduced silently (per the repo's AGENTS.md rule). Confidence: 0.5
- Gates `.env` / `.env.example` changes through explicit instruction: the agent should not touch them on its own, but the user will explicitly authorize/request the edits when wanted (has both denied and then explicitly requested such writes). Confidence: 0.6
- Prefers consistent tooling configuration shared across apps (identical Prettier config, matching ESLint rule severities) so the whole monorepo behaves uniformly. Confidence: 0.45
- Prefers monorepo-wide root scripts (`lint`/`build`/`format`/`test`/`dev`, plus `db:up`/`db:down`) driven through the package manager's recursive/workspace flags. Confidence: 0.4
- Prefers large-scope implementation work executed incrementally step by step (one phase/unit at a time, verifying the build after each step) rather than as a single big-bang change. Confidence: 0.55
- Prefers fast tests that run locally without external infrastructure; when a test would require a live database (e.g. Postgres e2e), prefers covering it with a DB-free unit test now and deferring the e2e version to CI rather than blocking or skipping coverage entirely. Confidence: 0.45
- Wants bulky sample/dummy data (e.g. hundreds of records) produced via a committed, re-runnable seed script that also creates any missing dependent master data, rather than manual entry, so dev environments can be populated quickly. Confidence: 0.4
- Expects the documentation set (PRD, design docs, conventions, planning) to stay mutually synchronized, and will explicitly ask the agent to audit the docs folder for drift and reconcile inconsistencies against the source of truth. Confidence: 0.5
- Prefers work that fully conforms to the canonical standard (the PRD, the conventions doc, or industry-standard monorepo practice) over partial, behavior-only, or shortcut implementations when the two diverge. Confidence: 0.5
- Drives work by referencing the persisted plan document and issuing short continuation directives ("next step", "continue", "execute phase N"), expecting the agent to resume from the plan and proceed to the next unit without re-explanation; may also jump phases out of plan order (e.g. "execute phase 7 first") and expects the requested order honored, and opens resumed sessions by asking for a concise recap of what was done last session. Confidence: 0.55
- Expects compiler/IDE deprecation warnings fixed at the root cause (e.g. dropping a deprecated `tsconfig` option like `baseUrl`) rather than silenced with suppression flags such as `ignoreDeprecations`. Confidence: 0.45
- Gives fine-grained UI polish instructions (e.g. surface an employee-number column, color-code enum values) and expects them implemented exactly as specified, preferring status/type values rendered as color-coded Ant Design tags. Confidence: 0.45
- Prefers explicit hex color values (e.g. `#eb2f96`) over Ant Design preset color-name tokens for tag/color styling, asking for named colors to be converted to hex format. Confidence: 0.5
- Prefers dedicated full pages/routes over modals for entity flows: when choosing between a modal and a page, picks the page — keeps Create navigating to its own route (with the parent record pre-filled) and wants View to open a read-only details page rather than a modal. Confidence: 0.55
- When facing a structural/design decision (e.g. menu/routing/information architecture), asks for a real-world "best practice" recommendation and expects the agent to justify it against the project's own docs (PRD/design docs/routes) plus general convention, giving a clear recommended option and an explicit "what to avoid," rather than a bare opinion. Confidence: 0.5
- Prefers the frontend organized by domain under `features/<domain>/` (each domain with its own pages/, components/, api module, and barrel index.ts), keeping all modules of a domain together rather than nested under an unrelated feature (e.g. moving contract files out of `features/employees` into `features/contract`). Confidence: 0.45
- Prefers record navigation exposed as an explicit action button in the row actions (e.g. a "Details" button next to edit/delete, mirroring the existing Criteria "Open" pattern) rather than making a data cell like the name a clickable link; wants the read-only Details action visible to every role while edit/delete stay gated to write roles (ADMIN/HR). Confidence: 0.5
- When asking for a design/architecture decision, explicitly authorizes the agent to edit the PRD, design docs, or routes to implement the chosen approach — treating docs and route definitions as in-scope to change (in contrast to gated areas like new dependencies and `.env`, which need explicit approval). Confidence: 0.45
- Prefers a "view" action to reuse existing pages/navigation (e.g. deep-linking to a sibling page's tab via `?tab=contracts`, mirroring how the edit-employee page behaves) rather than adding a new dedicated read-only detail page/route; favors consistency with an established page's pattern over a new bespoke screen. Confidence: 0.45
